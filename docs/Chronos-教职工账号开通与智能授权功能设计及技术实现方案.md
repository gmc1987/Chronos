# Chronos 教职工账号开通与智能授权

## 功能设计方案与技术实现方案

- 适用系统：Chronos 智慧校园平台
- 方案版本：V1.0
- 生成日期：2026-11-05
- 文档状态：待评审

---

## 1. 设计结论

本方案采用“基础角色兜底 + 智能体生成授权提案 + 人工确认执行”的组合模式。

1. 教职工导入只负责人员、任职、账号和基础访问能力。
2. 取消岗位与角色的系统级映射。岗位属于组织人事域，角色属于功能授权域，二者不建立自动、持久、强耦合关系。
3. 新建或启用的教职工账号统一授予低权限基础角色，保证能够登录并访问公共功能。
4. 业务角色仍然直接授予用户，现有用户—角色—权限关系保持不变。
5. 学期运营智能体负责把管理员明确表达的自然语言规则转换为待确认授权方案，不自行猜测角色。
6. 任何智能授权必须经过预览；高风险授权必须经过异人审核。
7. 数据范围与功能角色分开演进，不通过逐条权限直授弱化现有 RBAC。

## 2. 背景与问题

### 2.1 当前设计的问题

- 岗位与角色语义不同，却通过岗位角色映射形成自动授权关系。
- 一人多岗时会叠加多个岗位角色，容易产生权限扩大。
- 岗位变化会隐式改变用户权限，授权来源不直观、难审计。
- 同一岗位人员可能承担不同业务职责，无法用岗位准确表达权限。
- 管理员导入岗位后还需逐项配置映射，初始化成本高。
- 未配置映射时，员工导入产生大量重复警告，但系统无法合理自动补齐。

### 2.2 目标

- 教职工批量导入后，账号可以立即登录并使用最基础功能。
- 岗位和任职变化不再自动改变业务权限。
- 管理员无需在 Excel 或页面中维护角色编码。
- 通过自然语言规则完成大批量用户角色分配。
- 智能授权具备预览、审批、审计和回滚能力。
- 基础授权、人工授权和智能体授权互不覆盖。

### 2.3 非目标

第一阶段不实现以下能力：

- 根据岗位名称自动猜测角色。
- 让大模型直接生成 SQL、数据库 ID 或执行脚本。
- 将菜单和 API 权限点逐条直接授予用户。
- 自动撤销人工授予的角色。
- 自动授予超级管理员、平台管理员等关键权限。
- 自然语言未经预览和审批直接执行。
- 完整用户级资源权限体系。

## 3. 权限模型设计

### 3.1 三个独立维度

| 维度 | 负责内容 | 维护方式 |
|---|---|---|
| 账号身份 | 用户是谁、是否可登录、绑定哪个教职工 | 教职工导入自动处理 |
| 功能角色 | 可以使用哪些业务功能 | 人工授权或经审批的智能授权 |
| 数据范围 | 可以操作哪些机构、部门、课程或班级 | 后续独立建设 |

### 3.2 任职数据的正确用途

任职信息只能作为授权规则的筛选条件，例如：

- 部门等于教务处。
- 岗位等于专任教师。
- 当前有效任职。
- 主任职为是。
- 部门负责人为是。

任职本身不能直接成为授权来源。最终持久化结果仍是明确的用户—角色关系。

### 3.3 授权来源

保留 `t_user_role_assignment_source`，将来源类型调整为：

| 来源类型 | 含义 | 处理原则 |
|---|---|---|
| `BASE_ACCOUNT` | 账号开通时授予的基础角色 | 系统维护，导入不得删除 |
| `MANUAL` | 管理员在用户管理中直接授予 | 人工维护，智能体不得覆盖 |
| `AGENT_GRANT` | 智能授权提案审批执行后授予 | 按提案审计和回滚 |
| `POSITION_MAPPING` | 旧岗位映射产生的历史来源 | 停止新增，迁移后废弃 |

同一用户—角色可以同时存在多个来源。删除某个来源时，只有该用户—角色已无其他有效来源，才删除实际 `t_user_role` 关系。

## 4. 用户流程设计

### 4.1 教职工批量导入

“批量导入并开通账号”对话框只保留：

- 创建或同步账号。
- 停离职人员是否停用账号。
- 来源系统。

删除：

- 同步岗位角色。
- 岗位角色映射配置。
- “未配置有效的岗位角色映射”警告。

正式导入流程：

1. 导入或更新教职工。
2. 导入或更新任职。
3. 为缺少账号的教职工创建账号。
4. 为新账号及缺少基础角色的活动账号补充 `ROLE_PLATFORM_USER`。
5. 不修改其他业务角色。
6. 正式导入后一次性返回新账号临时密码。
7. 预检不消耗永久编号、不创建账号、不返回密码。

界面固定说明：

> 新账号将自动获得基础教职工角色，可登录并使用公共功能。业务角色可在用户管理中人工分配，或使用学期运营智能体批量授权。

### 4.2 基础角色

第一阶段直接使用现有内置角色 `ROLE_PLATFORM_USER`，避免创建语义重复的角色。

上线前必须检查并收敛该角色，确保只包含：

- 登录及刷新令牌。
- 统一门户基础页面。
- 个人资料与密码修改。
- 通知、公告等公共只读能力。
- 用户本人相关的最小接口。

不得包含：

- 用户、角色和权限管理。
- 跨部门数据查询。
- 审批、发布、删除等业务写权限。
- 教务、财务、人事等专业管理权限。

如现有 `ROLE_PLATFORM_USER` 权限过宽，应先收敛该角色，而不是新增岗位映射。

### 4.3 人工角色分配

现有用户管理继续作为个别用户授权入口：

- 管理员选择角色中文名称。
- 保存后记录 `MANUAL` 来源。
- 人工授权不受账号导入或智能授权执行影响。

### 4.4 智能体批量授权

管理员在学期运营智能体中输入明确规则，例如：

> 给所有当前在职的专任教师授予“成绩教师”；给教务处主任和副主任授予“教务审批人”；不要处理已经离职的人员。

系统流程：

1. **理解规则**：将自然语言解析成受限结构化规则。
2. **实体解析**：服务端解析真实角色、机构、部门、岗位和人员。
3. **歧义处理**：同名、多义或不存在的实体必须要求澄清。
4. **影响预览**：生成拟新增、已拥有、无法处理和高风险项。
5. **人工确认**：展示按规则和用户分组的清单。
6. **风险审批**：高风险角色必须由独立审核人审批。
7. **批量执行**：写入用户—角色关系和 `AGENT_GRANT` 来源。
8. **审计与回滚**：保存规则原文、解析结果、审批人和逐项变更。

管理员不输入角色编码。界面展示角色中文名称，服务端解析为角色 ID；匹配不到或存在同名时必须澄清。

## 5. 智能授权规则与安全边界

### 5.1 受限规则结构

大模型只能输出受限 JSON，不允许输出 SQL、数据库 ID 或任意执行脚本。

```json
{
  "rules": [
    {
      "sourceText": "给所有当前在职的专任教师授予成绩教师",
      "action": "GRANT_ROLE",
      "subject": {
        "employmentStatus": ["ACTIVE"],
        "positionNames": ["专任教师"],
        "currentAssignmentOnly": true
      },
      "roleNames": ["成绩教师"]
    }
  ]
}
```

允许的主体条件：

- 机构名称或编码。
- 部门名称或编码。
- 岗位名称或编码。
- 教职工类型。
- 在职状态。
- 主任职。
- 部门负责人。
- 当前有效任职。
- 明确点名的姓名、工号或导入标识。

第一阶段只允许：

- `GRANT_ROLE`

第二阶段再考虑：

- `REVOKE_AGENT_ROLE`：只撤销指定智能提案授予的角色。
- `REVOKE_ROLE`：高风险动作，必须明确范围和异人审批。
- 数据范围授权动作。

### 5.2 服务端确定性校验

大模型输出后，服务端必须：

- 检查每条规则保留对应自然语言原文。
- 按名称或编码查询真实实体。
- 拒绝不存在或多义的实体。
- 检查操作人是否有权管理目标用户。
- 检查操作人是否有权授予目标角色。
- 检查角色状态是否启用。
- 识别角色风险等级。
- 计算准确命中人数和用户列表。
- 合并重复规则，阻断相互冲突的规则。
- 禁止模型提供的数据库 ID 直接进入执行链路。

### 5.3 风险等级

建议为角色增加 `risk_level`：

| 风险等级 | 典型角色 | 执行要求 |
|---|---|---|
| `LOW` | 普通只读或使用角色 | 发起人确认后可执行 |
| `MEDIUM` | 普通业务写入角色 | 发起人确认后可执行并强化审计 |
| `HIGH` | 审批、发布、跨部门访问角色 | 必须异人审批 |
| `CRITICAL` | 超级管理员、平台和权限管理角色 | 第一阶段禁止智能体授予 |

基础角色自动授予，不需要审批。任何批量撤销至少按 `HIGH` 风险处理。

## 6. 预览与审批界面

### 6.1 预览摘要

展示：

- 规则数量。
- 命中用户数。
- 拟新增角色关系数。
- 已拥有、无需变更的关系数。
- 无法解析的用户或角色。
- 高风险角色数量。
- 超出操作人管理范围的用户数量。

### 6.2 明细表

| 用户 | 工号 | 部门 | 当前任职 | 拟增加角色 | 已有角色 | 风险 | 原因 |
|---|---|---|---|---|---|---|---|
| 张老师 | 202600001 | 计算机学院 | 专任教师 | 成绩教师 | 平台用户 | LOW | 命中规则1 |

支持按规则、部门、角色和风险筛选。

### 6.3 审批规则

- 基础角色自动授予，不需要审批。
- `LOW/MEDIUM` 批量新增：发起人确认后可执行。
- `HIGH`：必须异人审批。
- `CRITICAL`：第一阶段禁止智能体授予，只允许用户管理中人工处理。
- 任何批量撤销：至少按 `HIGH` 处理。

## 7. 技术架构

### 7.1 模块职责

| 模块 | 职责 |
|---|---|
| `platform-iam` | 账号创建、基础角色、规则实体解析、用户命中查询、授权预览、角色写入、来源记录、审计和回滚 |
| `education-operation-agent` | 自然语言交互、计划步骤编排、调用受控 IAM 工具、风险审批和结果展示 |
| `agent-runtime` | 复用工具白名单、执行状态机、工具调用审计、审批后执行和失败处理 |

IAM 业务逻辑不得写入教育智能体模块。学期运营智能体只是受控调用方，避免权限域与教育域反向耦合。

### 7.2 新增智能体工具

#### `iam.staff.authorization.context`

只读工具，返回：

- 操作人可管理的机构和部门。
- 启用角色的名称、描述和风险等级。
- 可用于筛选的岗位和人员属性。
- 不返回密码、密钥等敏感数据。

#### `iam.staff.authorization.plan`

只读工具，输入自然语言解析后的受限规则，输出：

- 标准化规则。
- 解析到的真实实体。
- 歧义和待澄清项。
- 综合风险等级。

#### `iam.staff.authorization.preview`

只读工具，输出：

- 命中用户。
- 当前角色。
- 拟增加角色。
- 无变更项。
- 被权限或数据范围阻止的项。
- 预览版本和基线摘要。

#### `iam.staff.authorization.execute`

写入工具，要求：

- 提案已确认。
- 预览版本未过期。
- 当前用户具有批量授权执行权限。
- 高风险步骤已经异人审批。
- 执行参数只能引用服务端生成的提案 ID 和版本。

#### `iam.staff.authorization.rollback`

写入工具，只回滚指定提案产生的 `AGENT_GRANT` 来源。

如果用户—角色还有 `MANUAL`、`BASE_ACCOUNT` 或其他提案来源，不删除实际角色关系。

## 8. 数据模型

### 8.1 `t_iam_authorization_proposal`

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 提案主键 |
| `request_text` | 管理员原始自然语言 |
| `normalized_rules_json` | 标准化受限规则 |
| `status` | 提案状态 |
| `risk_level` | 综合风险等级 |
| `created_by` | 发起人 |
| `reviewed_by` | 审核人 |
| `approved_at` | 审批时间 |
| `executed_at` | 执行时间 |
| `expires_at` | 提案过期时间 |
| `preview_version` | 预览版本 |
| `baseline_hash` | 执行前基线校验摘要 |
| `summary_json` | 影响统计 |
| `failure_message` | 失败原因 |
| `row_version` | 乐观锁版本 |

状态建议：

```text
DRAFT
  -> NEEDS_CLARIFICATION
  -> PREVIEWED
  -> AWAITING_APPROVAL
  -> APPROVED
  -> EXECUTING
  -> SUCCEEDED / FAILED
  -> ROLLED_BACK
```

补充状态：

- `REJECTED`
- `EXPIRED`

### 8.2 `t_iam_authorization_proposal_item`

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 明细主键 |
| `proposal_id` | 所属提案 |
| `rule_index` | 来源规则序号 |
| `user_id` | 目标用户 |
| `role_id` | 目标角色 |
| `action` | 授权动作 |
| `before_present` | 执行前是否存在 |
| `after_present` | 执行后是否存在 |
| `result` | 执行结果 |
| `reason` | 原因或错误 |
| `executed_at` | 执行时间 |

唯一约束：

```text
proposal_id + user_id + role_id + action
```

### 8.3 `t_user_role_assignment_source`

继续使用，但需要：

- 支持 `BASE_ACCOUNT`、`MANUAL`、`AGENT_GRANT`。
- `AGENT_GRANT` 的 `source_key` 保存 proposal ID 或 proposal item ID。
- 增加用户、角色、来源类型、来源键的唯一约束。

### 8.4 基线校验

预览时生成 `baseline_hash`，至少包含：

- 命中用户及其有效任职摘要。
- 目标角色状态。
- 用户当前角色关系。
- 操作人的可管理范围。

执行前重新计算。如果人员、任职、角色状态或权限范围已变化，则拒绝执行并要求重新预览。

### 9.1 删除岗位角色映射链路

前端：

- 删除 `AdminDirectory.vue` 岗位列表的“角色映射”按钮。
- 删除岗位角色映射对话框、状态和 API 调用。
- 删除员工导入中的“同步岗位角色”选项。
- 删除岗位映射相关警告展示。

后端：

- 删除 `IamDirectoryController` 的岗位角色映射 CRUD。
- 删除 `PositionRoleMappingService` 及仓储的运行时引用。
- 删除 `StaffAccountProvisioningService.syncPositionRoles(...)`。
- 删除 `EmployeeImportService.ImportOptions.syncRoles`。
- 删除导入接口对 `iam:directory:role-sync` 的条件权限检查。
- `DirectoryImportService` 保留人员和任职导入，不再参与业务角色同步。

数据库：

- 首次迁移将所有有效 `POSITION_MAPPING` 来源转换为 `MANUAL`，避免删除映射功能后用户突然失权。
- 停止读取和写入 `t_position_role_mapping`。
- 稳定一个发布周期后删除表、实体、仓储和相关权限。

### 9.2 基础角色授予

在 `StaffAccountProvisioningService` 中增加：

```java
ensureBaseRole(account, "ROLE_PLATFORM_USER", dryRun);
```

规则：

- 新账号必须授予。
- 已有活动教职工账号缺少时补齐。
- 停离职账号停用时，不必删除基础角色；账号状态负责阻止登录。
- 写入 `BASE_ACCOUNT` 来源。
- 不覆盖 `MANUAL` 或 `AGENT_GRANT`。
- 找不到基础角色或角色被停用时，整批导入失败，不能创建无基础权限账号。

### 9.3 人工角色保存

`AdminUserServiceImpl` 的用户管理保存操作只管理 `MANUAL` 来源：

- 页面提交的角色集合只改变人工授权。
- 不删除 `BASE_ACCOUNT`。
- 不删除 `AGENT_GRANT`。
- 实际 `t_user_role` 是所有有效来源的并集。

## 10. 权限与安全要求

建议新增：

- `iam:authorization-agent:view`
- `iam:authorization-agent:plan`
- `iam:authorization-agent:execute`
- `iam:authorization-agent:review`
- `iam:authorization-agent:rollback`

安全要求：

- 工具调用必须使用真实登录身份。
- 操作人只能给自己有权管理的用户授权。
- 操作人不能授予自己无权授予的角色。
- 智能体不能扩大操作人的权限边界。
- 高风险审核人与发起人不能相同。
- 临时密码不得进入智能体上下文、日志或提案表。
- 规则原文、解析结果、预览、审批和执行都必须记录审计日志。
- 批量执行设置最大用户数和最大关系数；超限必须拆批或再次确认。

## 11. 数据范围后续方案

不建议把菜单或 API 权限点直接授予用户。继续保持：

- 角色决定“能做什么”。
- 数据范围决定“能对哪些数据做”。

当前 `RoleDataScope` 是角色级范围。个性化需求出现后，可新增用户—角色—数据范围授权记录，例如：

- 用户 A 拥有“教务审批人”，范围为计算机学院。
- 用户 B 拥有同一角色，范围为全校。

后续授权记录应包含：

- 用户。
- 角色。
- 机构、部门、班级或课程等资源范围。
- 授权来源。
- 有效期。
- 审批记录。

该能力属于后续阶段，不与当前账号导入强耦合。

## 12. 分阶段实施计划

### 第一阶段：纠正账号导入授权边界

1. 删除岗位角色映射前后端入口。
2. 删除员工导入的岗位角色同步选项和警告。
3. 为所有活动教职工账号保证 `ROLE_PLATFORM_USER` 基础角色。
4. 修改人工角色保存逻辑，按来源合并，防止覆盖基础角色。
5. 迁移已有 `POSITION_MAPPING` 授权为 `MANUAL`。
6. 更新 Excel 填写说明和用户文档。
7. 增加账号创建、重复导入、停离职、人工角色保护测试。

第一阶段完成后，现有批量导入即可稳定创建账号并保证基础登录能力。

### 第二阶段：智能授权提案

1. 新增授权提案和明细表。
2. 实现规则解析、实体解析和预览服务。
3. 增加受控 IAM Agent Tool。
4. 接入学期运营智能体计划和审核状态机。
5. 增加预览、确认、审核、执行和回滚界面。
6. 增加角色风险等级和高风险限制。
7. 完成审计、基线漂移校验及幂等测试。

### 第三阶段：用户级数据范围

1. 根据真实业务需求设计用户—角色—范围授权。
2. 扩展 `IDataScopeService`。
3. 智能体规则支持数据范围提案。
4. 增加有效期、申请、审批和自动回收。

## 13. 验收标准

### 13.1 第一阶段

- 导入 175 名教职工时不再出现岗位映射警告。
- 新账号全部绑定教职工并获得基础角色。
- 已有业务角色不被导入覆盖或删除。
- 重复导入不重置密码、不重复创建账号和来源记录。
- 岗位或任职变化不会自动增加或删除业务角色。
- 停离职账号按选项停用并撤销令牌。
- 岗位页面不再显示角色映射入口。

### 13.2 第二阶段

- 管理员只需输入角色中文名称和人员筛选规则，不需要角色编码。
- 同名或不存在实体会要求澄清，不会猜测执行。
- 预览结果准确展示每个用户的前后变化。
- 未审批提案无法执行。
- 高风险授权要求异人审核。
- 执行前数据变化时必须重新预览。
- 回滚只移除该提案的授权来源，不影响人工和基础授权。
- 全链路可审计。

---

## 14. 最终业务原则

> 导入负责身份和基础访问；角色始终授予用户；任职只用于筛选和辅助决策；智能体生成方案但不绕过确认；数据范围独立于功能角色演进。
