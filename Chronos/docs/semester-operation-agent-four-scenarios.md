# 学期运营智能体下一阶段业务目标

## 总目标

把学期运营智能体从“生成一份计划”升级为四类真实业务的可交互执行入口：用户用自然语言描述目标，智能体识别学期和业务场景，读取当前业务数据，按依赖拆分阶段，逐步展示检查结果；涉及正式写入的步骤先形成候选结果，由用户或有权限的审核人确认后再写入。每一步都必须保留人工菜单入口，智能体不能绕过现有领域服务、权限、审批、审计和幂等校验。

## 场景一：新生入学

| 阶段 | 智能体步骤 | 正式数据边界 | 人工入口 |
| --- | --- | --- | --- |
| 1.基础准备 | 学期、专业、班额、账号策略和政策检查 | 只读 | 学期管理、专业管理、班级管理、账号策略 |
| 2.新生数据接入 | 上传 XLSX、格式校验、重复学号/身份证检查，生成导入候选 | 候选，不写正式学籍 | 新生/录取名册导入 |
| 3.行政班分班 | 按专业、培养层次、班额生成分班候选，展示每名学生去向 | 候选，确认后写分班关系 | 班级管理、学生分班 |
| 4.报到建档 | 资格复查、报到状态、学籍档案和校内学号生成 | 候选，审核后写入 | 新生报到/学生档案 |
| 5.账号绑定 | 创建学生账号、绑定用户资料、检查一对一关系 | 写入受控领域服务 | 用户/账号管理、学生账号 |
| 6.住宿处理 | 调用 `admission.accommodation.check` 检查容量，再由 `admission.accommodation.plan` 生成学生—床位候选；`admission.accommodation.assign.batch` 只有在候选确认后才允许正式写入 | 候选；确认后批量写入住宿关系 | 住宿分配 `/admin/education/accommodations` |

完成标准：候选数据可逐行复核；确认后可重试且不重复建档；任一阶段失败可暂停并从失败阶段恢复。

## 场景二：走班排课

1. 检查学期、教师、教室、课程、教学任务、教学班、节假日和日期级规则。
2. 生成人工可读的教学任务与教师分工候选。
3. 生成教学班、选课关系和学生课表范围候选。
4. 调用现有全量规则自动排课求解器，展示硬约束冲突、软约束评分和未排课课时。
5. 提交候选方案，由独立审核人审核；方案负责人不能审核自己的方案。
6. 审核通过后应用候选版本并发布正式课表；考试、请假代课、节假日调课均走日期级变更链路。

人工入口：课程/教学任务、教学班、走班排课、规则配置、自动排课候选、课表审核与发布。

## 场景三：教师入职

1. 导入或录入入职员工，校验身份证、部门、岗位和在职状态。
2. 按学校配置的工号规则生成唯一 `employeeCode`；教师档案默认使用工号，不再维护第二套教师编号。
3. 生成教师账号和用户资料绑定候选，检查一对一关系。
4. 补充任教资格、学科方向、最大周课时和可用时间。
5. 生成本学期教师分工候选，交由教务人员确认后进入教学任务和排课。

人工入口：机构员工管理、教师管理、账号管理、教师资格/排课约束、教学任务。

## 场景四：学期末运营

1. 期末上下文检查：课程开课、成绩册、学籍异动和领域事件死信。
2. 考试收口检查：考试计划、场次、考场、监考分配和待处理监考变更。
3. 成绩收口检查：成绩确认、发布和未发布成绩册。
4. 毕业学籍准备：按入学年份生成毕业学籍异动待办，必须经过原有学籍审批。
5. 归档前置检查：未完成异动、死信事件和仍有业务写入风险时阻止归档。
6. 归档与下学期交接：由教务管理员在现有菜单人工确认执行，智能体只提供候选和检查结果，不直接改写历史数据。

人工入口：考试计划/场次、成绩中心、学籍异动、毕业管理、学期管理和归档菜单。

## 统一交互与治理要求

- 未识别学期时使用当前启用学期；识别到非当前学期先询问确认；识别到不存在的学期先询问是否创建，并在收齐起止日期、周数后才创建。
- 侧边智能体视图实时显示当前阶段、步骤状态、输入数据摘要、下一步计划、错误和恢复动作。
- “候选模式”只读或 dry-run；“正式执行”对每个写入步骤单独确认，并遵守审核人不能审核自己方案的规则。
- 所有工具必须在目录注册，按业务阶段排序；模型只能选择已注册工具，不能生成 SQL 或越权调用领域服务。
- 每个阶段都保留人工入口；智能体缺少领域模型时必须明确报告缺口，不能返回虚假的成功结果。
